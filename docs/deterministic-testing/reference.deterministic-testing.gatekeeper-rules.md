# CLAUDE.md — `outside` 基盤ライブラリ 門番規約（専用セッション用）

> 本ファイルは、共有基盤リポジトリ `outside`（展開先: `libs/outside/{go,angular,next,flutter}`）を管理する専用セッションに読み込ませる厳格な門番規約です。

---

## 0. 本リポジトリの役割と存在意義

`outside` は、複数の本体プロジェクトから `git archive`（タグ固定）経由で取り込まれる **OS・言語ランタイム境界の抽象化ライブラリ** である。
本体プロジェクト側の単体テストを 100% 決定論的かつキャッシュ可能に保つため、非決定的な外部操作を「本番実装（Real）」と「決定論的mock」のペアとして提供する。

**本体プロジェクト側では `outside` 自身の内部動作をテストしない（テスト免除済み基盤）。**
したがって本リポジトリ内のテストでは、`Mock` の決定論的挙動だけでなく、**`Real` が実際の OS・ランタイム上で正しく動作することを完全に保証しなければならない**。

---

## 1. 絶対禁止事項（門番ルール — 違反時は即リジェクト）

本体セッションから `relay` 経由で機能追加依頼を受けた際、以下のいずれかに該当するコードの追加を**いかなる理由があっても拒否・差し戻し**せよ。

1. **特定外部ツール・CLI 名を含むコードの禁止:**
   - `git`, `ffmpeg`, `docker`, `curl`, `aws`, `nx` など特定コマンド専用の関数・型・引数ビルダー（例: `GitRevParse()`, `RunDocker()`）を定義してはならない。
   - **正しい抽象化:** 汎用的な `Exec(cmd, args)` や `ExecWithStdin(cmd, args, stdin)` のみを定義し、コマンド組み立ては呼び出し元の本体プロジェクト（または `adapters/`）側で行わせること。
2. **業務ドメイン用語・Cookie・認証仕様の禁止:**
   - `User`, `Session`, `Order`, `Ledger`, `Cookie`, `Token` といった業務・プロトコル概念を含む型・メソッド・定数を書いてはならない。
3. **対象ランタイム外のフレームワーク依存禁止:**
   - **`go/`:** 標準ライブラリおよび `github.com/BurntSushi/toml`（`outside.toml` の読み取り）以外の外部パッケージを追加してはならない。
   - **`next/`:** `node:*` 標準モジュール以外の依存（特に **`next`, `react`, `@angular/*`**）を持ち込んではならない（`dependencies` は空。test だけが使う物は `devDependencies`）。
   - **`angular/`:** ブラウザ標準 Web API 型（`Storage`, `Location` 等）のみに依存し、**`@angular/core` や Node.js 固有モジュール（`node:fs` 等）** を持ち込んではならない。
   - **`flutter/`:** `dart:*` 以外の依存（特に **`package:flutter` やネイティブプラグイン類**）を絶対に `import` してはならない（`dependencies` は空）。Pure Dart を維持すること。
   - 依存の範囲の正本 = `design.outside.yaml` の `REQ-OUT-RUNTIME-DEPS`（検査 = `TC-OUT-RUNTIME-DEPS`）。
4. **本体プロジェクト固有設定のハードコード禁止:**
   - 特定のパス構造（`/app/config.json` 等）や特定の環境変数名（`NEXT_PUBLIC_*` 等）をデフォルト値として組み込んではならない。

---

## 2. 実装とテストの必須要件

新しい OS プリミティブを追加する場合は、必ず以下の 4 点を同時に実装・更新すること。

1. **インターフェース／型定義:** 最小限かつ言語標準の型を用いた明確なシグネチャ。
2. **Real 実装:** 実際の OS・ランタイム API を呼び出す本番用実装。
3. **Mock 実装:** 外部状態に一切依存せず、インメモリ状態・固定値・スタブ応答のみで動作するテスト用実装。状態変更・呼び出し履歴の検証ヘルパーを備えること。
4. **自己検証テスト（Real & Mock 両方のテスト）:**
   - 本リポジトリ内でのみ、実一時ディレクトリや実コマンドを用いた `Real` 実装のテストを許可する。
   - `Real` と `Mock` の双方が同一のインターフェース契約を満たすことをテストで保証すること。

---

## 3. リリース手順（マイクロ CI/CD 実行必須）

機能追加とテストの実装が完了したら、手動で `git tag` や `git push` を行わず、必ず以下の手順でリリースすること。

1. 変更内容をすべてステージングし、意図が明確なメッセージで `git commit` する。`CHANGELOG.md` に 部品・版・利用する側がやる事を書く。
2. `./scripts/release.sh <部品> <major|minor|patch>` を実行する（部品の表 = `design.outside.yaml` の `components`。足す = minor / 意味を変える・消す = major / 振る舞いを変えない直し = patch）。
3. スクリプトがその部品のテストを実行し、新規タグ（例: `lint-platform/v0.2.0`）を採番して Push する。手で `git tag` を打たない。部品の形でない tag が在れば スクリプトは止まる。
4. 出力された `RELEASE_SUCCESS: <tag>` を 依頼元の seat へ `ccark send` で返し 届いた事を確かめる。版を memory・CLAUDE.md 等へ書き写さない（版の正本 = operations.md §2）。

# 03. テストの目的と手段の分類・愚かなテストの排除基準

AI（Claude Code）にテストを書かせると、「何のためにそのテストを書くのか」という目的が曖昧なまま、実環境の状態をアサートする無意味なテストや、モックをそのまま返すだけのテストを量産しがちです。

本ドキュメントでは、**すべてのテストを 3 つの分類（A / B / C）に明確に定義**し、実装すべきテストと禁止すべきテストの判断基準を固定します。

---

## 1. テストの 3 分類マトリクス

| 分類 | 名称 | テストの目的 | 手段（データと依存の扱い） | 実行場所・キャッシュ |
| :--- | :--- | :--- | :--- | :--- |
| **分類 A** | **ロジック・振る舞い検証**<br>（全テストの 95%） | 入力データに対して、ビジネスロジック・状態遷移・アルゴリズムが仕様通り動くか検証する。 | `outside` と `adapters` の **`Fake`** を注入。時刻・ファイル・環境変数・ID・外部応答をすべて固定値にする。 | Unit テスト<br>**キャッシュ 100% 有効** |
| **分類 B** | **境界バリデーション・設定仕様検証** | 必須環境変数の欠落エラー処理や、ステージごとの設定組み立て仕様（Cookie 属性等）が正しいか検証する。 | **実環境（`process.env` や実 `.env`）は読まない。** テストケースごとに仮想の環境変数マップや引数（例: `stage="production"`）を注入して検証する。 | Unit テスト<br>**キャッシュ 100% 有効** |
| **分類 C** | **愚かなテスト（作成禁止）** | 価値がなく、キャッシュ破壊・保守コスト増大・偽の安心感を生むテスト。 | 実環境の値一致確認、モックのオウム返し、FW 内部挙動テスト、Unit 内での実外部接続。 | **作成・コミット禁止** |

---

## 2. 「設定の一致確認」に対する明確な判断基準

実運用で最も迷いやすい「環境変数や設定値に関するテスト」の判断基準を以下に固定します。

```text
[問い] ある設定値（例: API_URL, COOKIE_SECURE, TIMEOUT_MS）をテストしたい
  │
  ├─ Q1: その値は「実行環境（dev / stg / prod）ごとに変わる値」か？
  │    ├─ YES ──▶ 「環境によって値がセットされているか」をテストコードで見てはならない。
  │    │           必要なのは「未設定時に起動エラーになるか」「不正値でバリデーションが落ちるか」
  │    │           を仮想入力で検証する【分類 B（境界バリデーションテスト）】である。
  │    │
  │    └─ NO（全環境で必ず同じ値でなければならない不変の仕様）
  │         │
  │         ├─ そもそも環境変数にする必要はない。コード内の定数（const）にせよ。
  │         └─ 条件に応じて動的に組み立てる仕様（例: prodならSecure=true）であれば、
  │            仮想入力を渡して出力オブジェクトを検証する【分類 B（設定仕様テスト）】を書け。
```

### 具体例で見る「良いテスト（分類 B）」と「愚かなテスト（分類 C）」

- **NG（分類 C — 書いてはいけない）:**
  ```typescript
  // 実機の process.env や実 .env ファイルを読み込んでアサートしている
  // → 実行環境が変わると落ちる、または環境依存でキャッシュが壊れる
  test('環境変数が設定されていること', () => {
    expect(process.env.SESSION_SECRET).toBeDefined();
    expect(process.env.COOKIE_SAMESITE).toBe('Strict');
  });
  ```
- **OK（分類 B — 書くべき仕様テスト）:**
  ```typescript
  // 仮想環境変数マップを注入し、「設定組み立てロジックの仕様」を検証している
  // → どのマシンでいつ実行しても 100% 同じ結果になり、キャッシュが効く
  test('production指定時はSecureかつStrictなCookieオプションが生成されること', () => {
    const out = createFakeOutside();
    out.setEnv('APP_STAGE', 'production');

    const opts = buildSessionCookieOptions(out);

    expect(opts).toEqual({
      httpOnly: true,
      secure: true,
      sameSite: 'strict',
      path: '/',
    });
  });
  ```

## 3. 作成を禁止する「愚かなテスト（分類 C）」の 4 パターン

Claude Code は以下のテストを自動生成した場合、自己レビュー段階で必ず削除しなければなりません。

1. **実環境依存アサーション（Environment-Coupled Test）**
   - 実機の `process.env`、実ファイルシステム上の `/Users/...`、実行日の `new Date()` を期待値や入力値に使うテスト。
2. **モックのオウム返しテスト（Tautological Mock Test）**
   - `fake.exec` に `"ok"` を登録し、単に `fake.exec` を呼ぶだけのラッパーを呼んで `"ok"` が返ることを検証するテスト（変換ロジックや分岐ロジックを一切通っていない）。
3. **フレームワーク・標準ライブラリ自体のテスト**
   - Next.js のルーター仕様、Angular の DI コンテナの基本動作、Flutter 標準 `Text` Widget の描画、Go 標準 `json.Marshal` の仕様そのものを検証するテスト。
4. **Unit テストへの実外部接続の混入**
   - Unit テストファイル内で実 DB、実ソケット、実 HTTP、実 CLI コマンドを叩くテスト。

## 4. Integration テストの物理的隔離ルール

`outside` 自身の動作検証や、どうしても実外部ツール・実 OS との結合を確認したいテスト（Integration テスト）は、**Unit テストのキャッシュを一切汚染しないよう物理的に隔離**します。

| ランタイム | 普段回すキャッシュ対象（Unit） | 隔離された実環境テスト（Integration） |
| :--- | :--- | :--- |
| **Go** | `go test ./...`<br>（ビルドタグなし） | ファイル先頭に `//go:build integration` を付与。<br>`go test -tags=integration ./...` で明示実行時のみ稼働。 |
| **Next.js / Angular** | `vitest run`（`*.spec.ts` / `*.test.ts`） | `*.integration.spec.ts` にファイル名を分離し、別 Vitest プロジェクト設定で除外。 |
| **Flutter / Dart** | `flutter test --exclude-tags integration` | テストに `@Tags(['integration'])` を付与し、`dart_test.yaml` でデフォルト実行から除外。 |

> **AI への鉄則:** 通常の機能開発タスクでは Integration テストを書かず、すべて `Fake` を用いた **分類 A / 分類 B の Unit テスト** として実装すること。
